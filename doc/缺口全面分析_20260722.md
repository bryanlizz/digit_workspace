## 二、仍然缺失的关键能力（按严重程度排序）

### P0 — 阻塞核心业务闭环

| # | 缺失项 | 所属维度 | 说明 |
|---|--------|----------|------|
| 1 | **真实认证** | 基础设施 | 仍是 localStorage + 3 个硬编码用户，无 NextAuth/Auth.js 接入，无服务端 session，tRPC 无 auth guard。任何人都能调任何 API |
| 2 | **多租户隔离** | 基础设施 | 全局 DEFAULT_TENANT_ID，所有数据访问无租户过滤。多租户 SaaS 完全不可用 |
| 3 | **Mock Repo → Prisma 持久化** | 数据层 | employee、agent、project、audit、warRoomMessage 5 个 repo 仍是内存 mock，刷新即丢失 |
| 4 | **任务 retry/cancel 真实实现** | 执行引擎 | retryTask() 未实现，cancelTask() 只更新状态不中断执行 |
| 5 | **MCP 接入框架** | 执行层 | PRD 要求 MCP 作为工具运行时，当前完全未实现 |
| 6 | **AI Gateway Relay 工程化** | AI 基础设施 | Relay 模式缺 health/retry/streaming，配置不清晰 |

|---|--------|----------|------|

## 三、四端职责缺口（对照项目总览与端职责梳理）

### admin（平台总后台）— 缺口最大

当前只有：概览、计费、用户、权限 4 个页面（多为 stub）

缺失的入口：
- 模型路由 / AI 网关配置
- MCP Server 注册
- Tool Runtime 治理
- Connector Registry 管理
- 平台级审计与合规报告
- 部署治理（Docker/Helm/内网）
- Agent Worker 版本管理
- 系统设置

### enterprise（企业后台）— 缺口较大

当前有：概览、员工、权限、Agent、凭证、知识（多为 stub）

缺失的入口：
- 企业工具配置 / Agent 工具授权
- 浏览器自动化环境配置
- 企业审计 / 审批流配置
- Bad Case 管理与归因
- Agent Worker / 内网连接

### web（主产品端）— 相对完整但需清理

- legacy 页面无迁移提示
- 模型路由入口未迁入 admin
- 人类接管入口未产品化
- 任务结果详情页未完整实现

### desktop（个人客户端）— 最薄

- 基本是空壳，协作和知识页为 placeholder
- 无真实接管体验

## 四、架构层面的根本性缺失

### 4.1 无真实认证与授权

```
当前：localStorage 存用户名 → tRPC context 无 user → 所有 API 无保护
目标：NextAuth/Auth.js → tRPC auth middleware → RBAC → 操作级别控制
```

### 4.2 无多租户隔离

```
当前：DEFAULT_TENANT_ID 硬编码 → 所有租户共享数据
目标：请求解析 tenantId → Prisma 全局 where → 数据完全隔离
```

### 4.3 数据持久化严重不足

```
当前 7 个 repo 中：
- Prisma 真实持久化：task、knowledge（2 个）
- 内存 mock：employee、agent、project、audit、warRoomMessage（5 个）
```

### 4.4 执行层与展示层断裂

- Tool Runtime、Connector、Vault 代码已写好，但 Tool Executor 没有被 taskExecutor 真实调用
- 浏览器 Worker 是伪实现，Boss Connector 无法真正操作页面
- 飞书/邮件 Connector 已有代码但未接入真实凭证和端到端测试

### 4.5 通知链路断裂

- 审批创建后只能 console.log，用户收不到通知
- 任务完成/失败无推送
- 人类接管需求无法及时触达

## 六、一句话总结

> 数智企业的 UI 展示层和业务框架代码已基本完成（~80%），但"让 Agent 真正操作外部系统"的执行层仍存在关键断裂——认证、多租户、数据持久化、Tool Executor 接入、真实浏览器驱动和通知链路是 6 个必须优先解决的阻塞点。解决这些后，系统才能从"演示型驾驶舱"真正转变为"可商用的企业 Agent 操作平台"。
