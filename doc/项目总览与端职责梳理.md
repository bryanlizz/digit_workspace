# 数智企业 · 项目总览与端职责梳理

> 版本：V1.2
> 日期：2026-07-21

---

## 1. 项目一句话定义

数智企业是一个面向企业真实业务的 Agent 操作平台，用于创建、管理和约束数字员工，让 Agent 在权限、审批、审计、记忆、凭证和部署边界内，真实操作外部系统并完成业务闭环。

---

## 2. 产品定位

数智企业不是单纯的 3D 办公室、任务看板、知识库前端或演示壳，而是一个面向商用落地的企业级 Agent 操作平台。

核心目标：

- 让企业创建、配置和管理 Agent。
- 让 Agent 真实操作外部系统，例如飞书、Boss 直聘、CRM、邮件、短信、ERP、OA。
- 让所有关键动作具备权限控制、动作级审批、审计留痕和责任追溯。
- 让任务、工具调用、记忆、知识、Bad Case 和审计形成闭环。
- 支持 SaaS 多租户和私有化部署。

首批优先业务场景：

- 招聘：Boss 直聘、猎聘、飞书协同。
- 销售：CRM、邮件、客户跟进。

后续可扩展场景：

- 财务：金蝶、发票、付款申请。
- 行政：采购申请、OA、通知。
- HR：候选人管理、面试安排、Offer 流程。
- 客服：工单、企微、CRM 同步。
- 企业内部 OA、ERP、金蝶、用友等系统。

## 3. 核心业务原则

### 3.1 Agent 类型与责任链

Agent 分为两类：

- 员工分身：代表某个自然员工工作，责任归属于该员工，凭证、审计和权限与员工强绑定。
- 独立 Agent：独立工作，下属只能是 Agent，责任向上追溯到最近的自然人上司。

责任追溯原则：

- 员工分身的责任归属于对应自然人。
- 独立 Agent 的责任归属于最近的上级自然人。
- Agent 上下级关系、操作等级、凭证归属和审计查看权限都应围绕责任链设计。

### 3.2 权限不是摆设

系统要求对 Agent 施加操作级别限制：

- L0：只分析，不执行任何操作。
- L1：只读查询，可查询内部或外部系统。
- L2：写入内部系统。
- L3：发送内部消息。
- L4：发送外部消息。
- L5：修改业务数据，例如订单、合同、客户数据。
- L6：关键动作，例如资金、合同、人事。

权限控制要同时支持：

- 平台全局操作级别上限。
- 企业级操作级别策略。
- Agent 单独操作级别上限。
- 动作级审批规则。
- 权限 bitmap 或等价的细粒度权限模型。

### 3.3 审批是动作级

涉及外部消息、业务数据修改、资金、合同、人事等关键动作时，不能只做任务级审批，而要做动作级审批。

审批记录必须进入任务结果和审计链路。

### 3.4 审计必须完整

平台需要记录：

- 工具调用参数。
- 脱敏后的请求和响应。
- 页面截图。
- 浏览器录屏。
- 操作前后状态。
- 审批记录。
- 外部系统返回 ID。
- 任务执行过程回放。
- 审计报告导出。

审计规则：

- 数据默认保留 3 个月。
- 敏感字段需要脱敏。
- 审计日志不可篡改。
- 该 Agent 的所有上级应具备对应审计查看权限。

### 3.5 记忆、知识和 Bad Case 要闭环

记忆需要：

- 按 Agent 隔离。
- 按项目隔离。
- 可写入用户偏好、成功经验、失败案例、常用格式、客户或岗位上下文、工具使用注意事项。
- 不写入密码、Token、敏感个人信息、未授权候选人资料、客户隐私、财务敏感信息。

知识图谱需要：

- 从任务结果中抽取。
- 支持后续查询和复盘。
- 与任务执行链路联动。

Bad Case 管理需要：

- 从驳回任务、外部失败、发送失败、投诉、审批被拒等场景中自动识别。
- 自动归因。
- 人工确认是否进入记忆。
- 用于改进工具选择。
- 影响 Agent 评分。

## 4. 四端总体边界

### 4.1 web：主产品端 / 日常工作台

面向普通使用者、业务人员和团队成员。

web 负责“用产品”和“处理工作”，不是后台配置中心。

主要职责：

- 产品首页和组织工作台。
- 任务创建、任务触发、任务状态查看。
- 任务审批、驳回反馈和 Bad Case 人工确认。
- 人类接管入口，例如验证码、二次认证、登录失效、页面改版、风控弹窗、扫码登录。
- 协作空间。
- 员工广场、Agent 轻量浏览和技能入口。
- Agent 成长、表现、评分、风险和安全摘要展示。
- 知识浏览、记忆查询和结果消费。
- 任务结果展示，包括摘要、附件、外部记录、工具调用轨迹、审批、错误和后续动作。

当前主导航：

- 总部 `/`
- 协作 `/collaboration`
- 员工广场 `/employees`
- 技能广场 `/skills`
- 进化 `/evolution`
- 安全 `/security`
- 知识 `/knowledge`

web 不作为主入口承载：

- 模型路由配置。
- MCP Server 注册。
- Tool Runtime 治理。
- Connector Registry 管理。
- 平台权限策略。
- 平台计费管理。
- 平台用户管理。
- 企业凭证策略配置。
- 企业后台员工管理。
- 浏览器自动化环境配置。
- 私有化部署和 Agent Worker 管理。

legacy 页面说明：

以下 web 旧路径短期保留，避免深链失效，但不再出现在 web 主导航中：

### 4.2 admin：平台总后台

面向平台运营者和平台管理员。

admin 负责平台级资源、平台级策略、平台级工具运行时和部署治理，不绑定某一家企业的内部业务流程。

主要职责：

- 平台概览和运营指标。
- 多租户管理、平台用户管理、租户人员管理。
- 套餐与计费管理。
- 平台权限策略和全局操作级别上限。
- AI 网关、AI Key 管理、模型路由、配额控制。
- MCP Server 注册。
- 平台工具目录。
- Tool Runtime 治理，包括工具定义、注册、执行策略和审计规则。
- Connector Registry，包括连接器类型、动作定义、事件订阅、审批等级模板。

- 系统级审计、审计保留策略、脱敏规则、不可篡改策略和合规报告导出。
- SaaS 和私有化部署治理。
- Agent Worker 版本管理。
- Docker、Helm、部署包和内网连接策略。
- 系统设置。

- 平台概览 `/`

- MCP / Tool Runtime。
- Connector Registry。

- Agent 工具授权。

## 5. MCP、Tool Runtime 和 Connector 的端归属

MCP 不是某一个前端端的普通页面功能，而是执行层能力。

端归属如下：

- admin 负责平台级 MCP Server 注册、工具目录、Tool Runtime 治理、连接器类型和动作模板。
- enterprise 负责企业启用哪些工具、配置哪些连接实例、授权哪些 Agent 使用哪些工具。
- web 只在任务执行、审批、接管和结果查看中间接使用 MCP 工具。
- desktop 只在个人任务、接管和结果查看中间接使用 MCP 工具。

执行链路应是：

1. admin 注册 MCP Server 或 Connector 类型。
2. admin 定义工具动作、参数、操作等级、是否需要审批、审计规则。
3. enterprise 为企业启用工具或连接实例。
4. enterprise 给 Agent 授权可用工具和动作范围。
5. web 或 desktop 中的用户创建任务或处理审批。
6. Agent 执行任务时通过 Tool Runtime 调用 MCP 工具或 Connector。
7. 权限、审批、凭证、审计、截图录屏和外部记录写入统一任务链路。

## 6. 对照 PRD V2.0 的功能归属

### 6.1 登录 / 认证

- web：主产品入口。
- admin：平台管理登录。
- enterprise：企业后台入口。
- desktop：API 连接配置和登录态复用。

### 6.2 Agent 管理

- web：轻量浏览 Agent、查看能力、表现、风险和任务入口。
- admin：平台级规则模板和策略治理。
- enterprise：Agent 创建、配置、克隆、上下级关系、工作范围、操作等级、责任链和外部账号绑定。
- desktop：查看与执行相关 Agent，不做后台管理。

### 6.3 任务管理

- web：任务创建、任务触发、任务审批、状态查看、结果查看、驳回反馈。
- admin：不作为主场景，仅做平台审计抽查和治理统计。
- enterprise：企业管理视图，可查看企业域内任务、审批规则和执行风险。
- desktop：个人任务执行、轻量审批、接管和结果查看。

### 6.4 任务结果

- web：展示摘要、附件、外部记录、工具调用轨迹、审批记录、错误和后续动作。
- admin：用于平台级审计抽查。
- enterprise：用于企业审计、复盘和合规查看。
- desktop：轻量查看和个人处理。

### 6.5 外部系统集成

- admin：治理连接器类型、MCP Server、动作定义、事件订阅和审批等级模板。
- enterprise：配置企业连接实例、账号绑定、OAuth 授权和 Agent 工具授权。
- web：通过任务和结果间接使用外部系统能力。
- desktop：通过任务和接管间接使用外部系统能力。

首批外部系统：

- 飞书：官方 API，覆盖消息、审批、文档、通讯录。
- Boss 直聘：浏览器自动化，覆盖登录、搜索、打招呼、简历。
- 邮件：SMTP，覆盖邮件发送。
- 短信：云 API，覆盖短信发送。

后续扩展：

- CRM。
- ERP。
- OA。
- 金蝶。
- 用友。
- 企业知识库。

### 6.6 凭证管理 / Vault

- admin：平台级 Vault 策略、密钥后端、加密策略、Token 生命周期策略。
- enterprise：凭证存储、Agent 或外部系统绑定、OAuth Token 自动刷新、3 天失效提醒、凭证回收、离职交接。
- web：不管理凭证，只展示必要的授权状态和安全提醒。
- desktop：不管理企业凭证，只保留本地 API 连接设置。

凭证归属规则：

- 员工分身的凭证归属该员工。
- 独立 Agent 的凭证向上查找最近的自然人上司。
- Agent 不可见明文凭证。

### 6.7 人类接管机制

- web：处理审批、验证码、二次认证、登录失效、页面改版、风控弹窗、扫码登录等接管任务。
- desktop：提供本地或远程接管体验，适合验证码、扫码、风控弹窗等高频处理。
- enterprise：配置接管规则、接管人、上级派发逻辑和重试策略。
- admin：不作为日常接管入口，只做平台策略或审计治理。

### 6.8 记忆系统

- web：查看使用者可见的记忆摘要、任务上下文和知识引用。
- enterprise：配置企业记忆策略、Agent 和项目隔离、Bad Case 归因进入记忆的规则。
- admin：平台级记忆策略可选。
- desktop：只读摘要和个人任务上下文。

### 6.9 Bad Case 管理

- web：用户驳回、反馈、人工确认是否进入记忆。
- enterprise：自动归因、Bad Case 列表、确认流程、Agent 评分影响、工具改进跟踪。
- admin：跨企业统计和平台治理。
- desktop：轻量反馈。

### 6.10 审计与合规

- web：个人相关记录、任务摘要、审批记录和结果链路查看。
- admin：平台级审计、保留策略、脱敏规则、不可篡改策略和合规报告导出。
- enterprise：企业级审计、任务回放、截图录屏、外部记录、合规导出。
- desktop：只读摘要。

### 6.11 浏览器自动化

- admin：运行策略、浏览器环境版本、平台治理、执行器版本。
- enterprise：租户隔离、登录态持久化、截图录屏、代理或 IP 池、企业内网容器。
- web：查看截图、录屏、接管提示和执行结果。
- desktop：本地或远程接管入口，后续可承接轻量本地执行器。

### 6.12 模型路由 / AI 网关

- admin：AI Key 管理、配额控制、模型路由、平台配置。
- enterprise：可查看企业可用模型或配额，是否可配置取决于商业模式。
- web：`/settings` 当前作为 legacy 页面暂存，后续迁入 admin。
- desktop：不承载。

### 6.13 部署 / 私有化

- admin：SaaS 多租户、私有化部署包、Agent Worker 版本、Docker、Helm、内网连接策略、平台升级治理。
- enterprise：企业 Agent Worker、企业内网连接、数据同步、私有化环境配置。
- web：不承载。
- desktop：只保留本地连接设置。

## 7. 当前项目状态判断

### 7.1 已开始收敛的部分

- web 主导航已收敛为产品导航，不再展示管理分区。
- admin 导航文案已调整为平台总后台语义。
- enterprise 保持企业后台语义，继续承载企业员工、权限、Agent、凭证和知识库。
- desktop 保持个人任务、协作、知识和设置的轻入口定位。
- 四端仍复用当前 tRPC API Host 和 `AppRouter` 类型，避免前端职责收敛阶段同时引入后端边界风险。

### 7.2 已具备的基础

- 页面壳和路由结构已经有基础。
- 审计、记忆、任务、知识等主概念已经建立。
- 部分 API 和数据链路已完成。
- 外部系统接入的核心框架已开始建立。

### 7.3 仍需继续补的部分

- web legacy 管理页面的迁移提示或跳转。
- 模型路由入口从 web `/settings` 迁入 admin。
- MCP / Tool Runtime 接入框架：Server 注册、工具目录、工具调用、权限校验和审计链路。
- Connector Registry：飞书、Boss、邮件、短信、CRM、ERP 等连接器定义和动作模板。
- 人类接管机制：验证码、二次认证、登录失效、页面改版、风控弹窗、扫码登录。
- 浏览器自动化运行环境：租户隔离、登录态持久化、截图录屏、代理或 IP 池、企业内网容器。
- Bad Case 管理：驳回识别、自动归因、人工确认、进入记忆和影响 Agent 评分。
- 任务结果结构：摘要、附件、外部记录、工具调用轨迹、审批、错误和后续动作。
- 真实认证闭环。
- 外部系统真实接入。
- 执行引擎与工具运行时继续完善。
- 私有化部署、Agent Worker、SaaS 和私有化数据同步继续补齐。

### 7.4 主要问题

- 过去的实现更多是“先堆页面和能力”，端职责曾经不够清晰。
- 一些页面仍是“已接入 / 待接入”的过渡态。
- API Host 仍在 web 端，admin、enterprise、desktop 依赖 `@lobster/web/router` 类型；短期不应贸然拆分。
- MCP、Connector、浏览器自动化、Bad Case、人类接管等执行层能力还没有形成完整产品入口。
- 需要继续把功能边界、页面意义和真实数据链路重新对齐。

---

## 8. 后续推进顺序

1. 保持当前端职责边界，避免再把后台管理入口加回 web 主导航。
2. 给 web legacy 页面增加迁移提示：`/settings`、`/admin/billing`、`/admin/employees`、`/admin/permissions`。
3. 将模型路由入口迁入 admin，web `/settings` 保留为 legacy 提示页或跳转页。
4. 在 admin 设计 MCP / Tool Runtime 和 Connector Registry 的平台级入口。
5. 在 enterprise 设计企业工具启用、Agent 工具授权、浏览器自动化环境和 Agent Worker 配置入口。
6. 在 web / desktop 补任务审批、人类接管、Bad Case 确认和任务结果详情入口。
7. 按端补页面级功能清单，明确每个页面是“已接入真实数据”还是“演示 / 占位”。
8. 继续补真实认证、权限、凭证、审计、审批流和执行链路。
9. 等产品入口稳定后，再评估是否把 tRPC router 类型从 `apps/web` 迁到 `packages/api`。

---

## 9. API 与架构边界

短期保持以下边界不变：

- `/api/trpc` 仍由 web 端承载。
- `apps/web/src/server/api/root.ts` 仍是 API router 汇总点。
- admin、enterprise、desktop 仍通过 `@lobster/web/router` 依赖 `AppRouter` 类型。
- 暂不抽公共 Shell 到 `packages/ui`，避免不同端的产品语义再次被统一壳混淆。

后续如需拆分 API，应在四端入口和页面职责稳定后，再将 router 类型逐步迁入 `packages/api`，并保留 `@lobster/web/router` 的兼容导出。
